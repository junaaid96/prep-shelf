# 1. OWASP Top 10 (2025) — Every Risk with a Fix

The **OWASP Top 10:2025** is the current list. Two categories are new since 2021 — **Software Supply Chain Failures (A03)** and **Mishandling of Exceptional Conditions (A10)** — and **Security Misconfiguration** climbed from #5 to #2. Know the list, and know one concrete fix for each.

## A01 — Broken Access Control

The most common and most damaging class: a user does something they shouldn't be allowed to do.

**IDOR (Insecure Direct Object Reference):**

```python
# ✗ Any authenticated user can read any invoice by guessing an id
def get_invoice(request, invoice_id):
    return Invoice.objects.get(pk=invoice_id)

# ✓ Scope every query by the authenticated principal
def get_invoice(request, invoice_id):
    return get_object_or_404(Invoice, pk=invoice_id, clinic=request.user.clinic)
```

**Other forms:** missing function-level checks (the admin endpoint that only the UI hides), path traversal (`../../etc/passwd`), CORS misconfiguration that exposes an API to any origin, forced browsing, and privilege escalation through mass assignment (`{"role": "admin"}` in a PATCH body).

**Defences:**

- **Deny by default.** Every route requires an explicit grant; a new endpoint is unauthorised until someone adds the rule.
- **Enforce on the server, per request.** Client-side checks are UX, not security.
- **Scope in the query, not after fetching** — that's how list endpoints leak.
- Use **opaque or unguessable ids** (UUIDv7) as defence in depth — not as the control itself.
- **Return 404, not 403**, for resources the user may not know exist.
- **Test it**: for every endpoint, a test that user B cannot touch user A's data. This is the single highest-value security test suite you can write.

> **Asked as:** "What is IDOR?" · "How do you enforce multi-tenant isolation?" · "403 or 404 for a forbidden resource?"

## A02 — Security Misconfiguration

Now #2 because most breaches are boring: a default password, a public bucket, a debug endpoint left on.

```python
DEBUG = False                       # Django DEBUG=True leaks settings, SQL, and stack traces
ALLOWED_HOSTS = ["app.example.com"] # never ["*"]
```

Checklist:

- No default credentials anywhere. No sample/demo apps in production.
- **Stack traces and verbose errors off** in production — return a generic message plus a correlation id.
- Cloud storage private by default; audit for public buckets continuously.
- Security headers present (see below).
- Unused ports, services, admin panels, and debug/actuator endpoints closed or authenticated.
- Least-privilege IAM: no wildcard `*` policies, no long-lived keys.
- Configuration is **code**, scanned in CI (`tfsec`, `checkov`, `kube-score`).

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-{r}'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: geolocation=(), camera=(), microphone=()
Cross-Origin-Opener-Policy: same-origin
```

> **Asked as:** "Which security headers do you set?" · "What does `DEBUG=True` leak?" · "How do you keep configuration secure across environments?"

## A03 — Software Supply Chain Failures (NEW)

Your dependencies, build system, and CI are part of your attack surface. This category covers vulnerable components *and* compromised packages, poisoned build pipelines, malicious IDE/CI plugins, and typosquatting.

```bash
npm audit --audit-level=high
pip-audit
cargo audit
trivy image --severity HIGH,CRITICAL myapp:1.4.2
syft myapp:1.4.2 -o spdx-json > sbom.json      # know what you ship
cosign sign --yes myapp@sha256:…                # sign it
cosign verify --certificate-identity-regexp … myapp@sha256:…
```

Defences:

- **Lockfiles committed**, installs with `npm ci` / `uv sync --frozen` / `--require-hashes`.
- **Pin base images and actions by digest/SHA**, not mutable tags.
- **Automated dependency updates** (Dependabot/Renovate) with CI gating — an unpatched known CVE is the most-exploited category there is.
- **SBOM per release**, stored with the artifact, so "are we affected by CVE-2026-XXXX?" takes minutes.
- **Provenance/attestations** (SLSA, Sigstore) and signature verification at deploy/admission.
- **Least-privilege CI**: scoped tokens, OIDC instead of stored keys, no secrets available to fork PR builds, self-hosted runners isolated.
- **Vet new dependencies**: maintenance activity, maintainer count, install scripts, transitive weight. Every dependency is code you now run.

> **Asked as:** "How do you know what's in your build?" · "How do you protect against a malicious npm package?" · "What is an SBOM / SLSA provenance?"

## A04 — Cryptographic Failures

Sensitive data exposed because it wasn't encrypted, or was encrypted badly.

```python
# Passwords: slow, salted hashing — NEVER encryption, never SHA-256 alone
from argon2 import PasswordHasher
ph = PasswordHasher(time_cost=3, memory_cost=65536, parallelism=4)
hash_ = ph.hash(password)              # unique salt is embedded automatically
ph.verify(hash_, candidate)            # constant-time comparison
```

- **Passwords:** Argon2id (preferred), scrypt, or bcrypt. Never MD5/SHA-1/SHA-256 alone — they're fast, which is exactly wrong.
- **Data in transit:** TLS 1.3 everywhere, including internal service-to-service. HSTS. No mixed content.
- **Data at rest:** disk/database encryption plus column-level encryption for the truly sensitive fields (national ids, clinical notes).
- **Use AEAD** (AES-GCM, ChaCha20-Poly1305) — never ECB, never encryption without authentication.
- **Never invent crypto.** Use libsodium, `cryptography`, Tink, or your platform's KMS.
- **Random**: `secrets`/`crypto.randomBytes`/`SecureRandom`, never `Math.random()`/`random`.
- **Key management**: KMS/HSM, documented rotation, keys never in code or Git.
- **Post-quantum** is entering practice — TLS hybrid key exchange (ML-KEM) is being rolled out by major providers and JDK 27 ships PQ TLS support. Know the term; plan for crypto agility.

> **Asked as:** "How do you store passwords?" · "Why not SHA-256 for passwords?" · "Symmetric vs asymmetric — when do you use each?" · "What is AEAD?"

## A05 — Injection

Untrusted input interpreted as code or query. SQL, NoSQL, OS command, LDAP, XPath, template, and now **prompt injection** for LLM-backed features.

```python
# SQL — parameterise, always
cursor.execute("SELECT * FROM users WHERE email = %s", [email])          # ✓
cursor.execute(f"SELECT * FROM users WHERE email = '{email}'")           # ✗

# OS command — never build a shell string
subprocess.run(["convert", src, "-resize", "800x", dst], shell=False)    # ✓
os.system(f"convert {src} -resize 800x {dst}")                           # ✗

# NoSQL — cast/validate types; {"$gt": ""} as a password bypasses naive checks
db.users.find_one({"email": str(email), "token": str(token)})
```

**XSS** is injection into the browser:

```js
el.textContent = userInput;                       // ✓ safe
el.innerHTML = userInput;                         // ✗
el.innerHTML = DOMPurify.sanitize(userHtml);      // ✓ if you must render HTML
```

React escapes by default — `dangerouslySetInnerHTML` is the one hole, and CSP is the backstop.

**LLM prompt injection** (the modern variant): never let untrusted text control tool calls or privileged actions. Separate the instruction channel from the data channel, keep the model's tools least-privileged, validate outputs before acting on them, and require human confirmation for irreversible actions.

**Defence order:** parameterised queries/prepared statements → allow-list validation → context-aware output encoding → least-privilege database user (the app should not own `DROP TABLE`).

> **Asked as:** "How do you prevent SQL injection?" · "Is an ORM automatically safe?" (only until you use raw SQL or string-built filters) · "What is stored vs reflected vs DOM XSS?" · "What is prompt injection?"

## A06 — Insecure Design

Flaws you can't patch because the design is wrong: no rate limit on password reset, business logic that lets you apply a discount twice, a "forgot password" flow with guessable questions, no limits on resource consumption.

Fixes are process, not code:

- **Threat model** the feature before building it — STRIDE (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege) is a workable checklist in a 30-minute session.
- **Abuse cases** alongside user stories: "as an attacker, I want to…".
- **Secure defaults**: private by default, opt in to sharing; MFA on by default for admin roles.
- **Limits everywhere**: rate limits, quotas, maximum request/file sizes, pagination caps, timeouts.
- **Segregate by trust level** — the public API, the admin API, and the internal API should not be the same surface.

> **Asked as:** "What's the difference between insecure design and misconfiguration?" · "How would you threat model a payment feature?"

## A07 — Authentication Failures

Credential stuffing, brute force, weak session management, broken recovery flows.

- **MFA** — the single largest reduction in account takeover. TOTP at minimum; WebAuthn/passkeys are phishing-resistant and now widely supported.
- **Password policy per NIST SP 800-63B**: minimum length (8+, encourage passphrases), **check against breach lists** (Have I Been Pwned k-anonymity API), no forced periodic rotation, no arbitrary composition rules.
- **Rate limit + lockout with backoff** on login, reset, and OTP; per account *and* per IP (credential stuffing spreads across both).
- **Generic error messages**: "invalid email or password" — never "no such user" (that's a user-enumeration oracle). Keep response times constant.
- **Session management**: regenerate the session id on login (session fixation), `HttpOnly; Secure; SameSite=Lax`, idle + absolute timeouts, invalidate all sessions on password change, and give users a "sign out everywhere".
- **Password reset tokens**: single-use, short-lived (15–60 min), high-entropy, stored hashed, invalidated on use and on password change.

> **Asked as:** "How do you protect a login endpoint?" · "What is session fixation?" · "How does a secure password reset flow work?" · "Why not force 90-day password rotation?"

## A08 — Software or Data Integrity Failures

Trusting code or data that hasn't been verified: unsigned updates, insecure deserialisation, CDN scripts with no integrity check, CI that deploys unverified artifacts.

```html
<script src="https://cdn.example.com/lib.js"
        integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8wC"
        crossorigin="anonymous"></script>
```

- **Never deserialise untrusted data** into arbitrary types — Java serialization, Python `pickle`, PHP `unserialize`, and unsafe YAML loaders are all remote-code-execution primitives. Use JSON with a schema.
- **Verify signatures** on artifacts and container images before deploying.
- **Subresource Integrity** for third-party scripts, or self-host them.
- **Protected branches + required reviews** so code can't reach production unreviewed.

> **Asked as:** "Why is `pickle.loads` on user input dangerous?" · "What is SRI?" · "How do you ensure the artifact deployed is the one you built?"

## A09 — Security Logging & Alerting Failures

You can't respond to what you can't see. Breaches routinely go undetected for months.

Log (in structured form, with a trace id): authentication success and failure, authorisation denials, privilege changes, password/MFA changes, access to sensitive records, admin actions, payment events, and input-validation failures.

**Never log**: passwords, tokens, session ids, card numbers, or health data. Redact at the logger.

**Alert** on: authentication failure spikes, a single account failing across many IPs (or one IP across many accounts), privilege escalation, mass data export, access outside business hours, and log-volume dropping to zero (an attacker turning off logging, or your pipeline breaking).

Make logs **tamper-evident** — ship them off-host immediately, write-once retention, and restrict who can delete them. In regulated domains (healthcare, finance), an audit trail of who accessed which record is a legal requirement, not a nice-to-have.

> **Asked as:** "What security events do you log?" · "How would you detect credential stuffing?" · "How do you protect logs from tampering?"

## A10 — Mishandling of Exceptional Conditions (NEW)

Errors handled badly become vulnerabilities: verbose stack traces leaking internals, code that **fails open** instead of closed, unchecked return values, empty catch blocks, and race conditions in error paths.

```python
# ✗ Fails OPEN — an outage in the auth service grants everyone access
try:
    allowed = auth_service.check(user, resource)
except Exception:
    allowed = True

# ✓ Fails CLOSED, with a distinct signal
try:
    allowed = auth_service.check(user, resource)
except AuthServiceUnavailable:
    logger.error("authz unavailable", extra={"user": user.id})
    raise ServiceUnavailable("Authorisation temporarily unavailable")   # 503, not access
```

- **Fail closed** on every security decision.
- **Generic errors to the client, detail to the logs**, joined by a correlation id.
- **Never swallow exceptions.** An empty `catch` is a bug that hides bugs.
- **Check return values** — especially in C, where an unchecked `malloc`/`read` return is a classic vulnerability.
- Test the **error paths**, not just the happy path; that's where the security holes live.

> **Asked as:** "What does fail-open vs fail-closed mean?" · "Why are stack traces in production dangerous?" · "How do you return errors safely to a client?"

## Rapid-fire answers

| Question | Answer |
|---|---|
| CSRF | Forcing a logged-in user's browser to submit a request — stop with `SameSite` cookies + a per-session token |
| SSRF | Server fetches an attacker-supplied URL (e.g. cloud metadata at 169.254.169.254) — allow-list destinations, block link-local/private ranges, IMDSv2 |
| XXE | XML external entity → file read/SSRF — disable DTDs and external entities in the parser |
| Open redirect | `?next=https://evil.com` — validate against an allow-list of internal paths |
| Mass assignment | Binding a whole request body to a model — use explicit allow-lists / read-only fields |
| Timing attack | Leaking secrets via comparison time — use `hmac.compare_digest`/constant-time compare |
| Defence in depth | Multiple independent controls, so one failure isn't a breach |
| Least privilege | Every identity gets the minimum it needs, for the shortest time |
| Shift left | Security checks in the IDE/PR/CI, not a pentest a week before launch |
| Pentest vs SAST vs DAST vs SCA | Human attack / static code analysis / running-app scanning / dependency composition analysis |
